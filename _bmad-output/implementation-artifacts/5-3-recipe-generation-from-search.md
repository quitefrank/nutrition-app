# Story 5.3: Recipe Generation from Search

**Status:** ready-for-dev
**Story ID:** 5.3
**Epic:** 5 — Manual Search & Discovery

---

## Story

As a user browsing a restaurant's dish list,
I want to select a dish and get a full recipe,
So that I can save and cook a meal I've eaten or want to try — no camera required.

---

## Acceptance Criteria

**AC1 — Dish list renders in scan-results visual format (FR30)**
Given the user has navigated to a restaurant's dish list page (via 5.2 restaurant search)
When the restaurant dish list renders
Then dishes are shown using the same `DishCard` visual format as scan results: 64×64pt thumbnail (`radius-xs`), dish name (`text-base`), one-line description (`text-xs text-secondary`), calorie estimate (`text-xs text-tertiary`)

**AC2 — Dish detail bottom sheet is identical to scan flow (FR31)**
Given the user taps a dish card on the restaurant dish list
When the dish detail bottom sheet opens
Then it uses the existing `DishDetailSheet` component unchanged: drag handle, 200pt full-width image (or placeholder), dish name (`text-hero`), evidence block, description, ingredient list, Save Recipe CTA (56pt `radius-xl`), See Full Details link

**AC3 — Save flow uses search-generated metadata**
Given the user taps "Save Recipe" from the search-originated dish detail
When the recipe is saved
Then `POST /api/recipes` is called with `confidenceMetadata: { confidenceSource: 'search-generated' }` and `restaurantGooglePlacesId` set to the searched restaurant's `googlePlacesId`; the same `useSaveRecipe` mutation from `@/hooks/use-recipes` is used — no new save route or hook is created

**AC4 — Nutrition unavailable label renders when nutritionAvailable is false (FR37, NFR12)**
Given the dish detail response contains `nutritionAvailable: false`
When the dish detail bottom sheet renders
Then a "Nutrition unavailable" label appears below where the calorie estimate would normally appear; all other dish detail content (name, description, ingredients, Save Recipe CTA) renders normally; the save flow is unaffected

**AC5 — Restaurant dish list is generated by a new dedicated API route**
Given the user navigates to `/search/restaurants/[googlePlacesId]`
When the page mounts and the online status is true
Then `GET /api/search/restaurants/[googlePlacesId]/dishes` is called; it returns `{ data: DishResult[] }` (a Gemini-generated list of typical dishes for that restaurant); the page renders the list using the dish card pattern

**AC6 — Loading and error states are handled**
Given the restaurant dish list fetch is in progress
When the page is in loading state
Then a loading indicator is displayed; if the fetch fails, an inline error message is shown with a retry button; the page never crashes

### Route Location and Naming

This story creates a **new** route:
```
src/app/api/search/restaurants/[googlePlacesId]/dishes/route.ts
```

This is a Next.js App Router dynamic segment route. The `[googlePlacesId]` folder creates the dynamic param. The full URL is:
```
GET /api/search/restaurants/[googlePlacesId]/dishes
```

The route handler receives the param via the second argument to the `GET` function:
```typescript
export async function GET(
  _req: NextRequest,
  { params }: { params: Promise<{ googlePlacesId: string }> }
) {
  const { googlePlacesId } = await params
  // ...
}
```

This is the Next.js 15 pattern for dynamic API route params — params are now a Promise. See `src/app/restaurants/[id]/page.tsx` for the same pattern in a page component.

### Gemini Prompt for Restaurant Dish List

This route generates a list of typical menu dishes for a restaurant. Use this prompt pattern:

```typescript
const prompt = `You are a culinary expert with knowledge of restaurant menus.
Generate a list of 6–10 typical dishes you would find at a restaurant with Google Places ID "${googlePlacesId}".

If you know this specific restaurant, generate its actual menu items.
If you don't recognise the ID, generate typical dishes for a casual dining restaurant.

Return ONLY valid JSON (no markdown, no explanation) in this exact format:
{
  "dishes": [
    {
      "name": "string — dish name",
      "description": "string — one sentence description",
      "calorieEstimate": number or null,
      "ingredients": [],
      "imageUrl": null
    }
  ]
}

Rules:
- ingredients is ALWAYS an empty array [] — ingredient detail is fetched separately per dish
- imageUrl is ALWAYS null
- calorieEstimate: best estimate in kcal, or null if unknown
- Generate 6–10 dishes
- Return valid JSON only`
```

Note: `ingredients` is `[]` because this is a browsable list. Ingredient detail is generated by `GET /api/search/dishes?restaurantId&name` (Story 5.1 route) when the user opens a dish detail. The list-level dish data intentionally omits ingredients.

**Parse the response** using the strip-markdown-fences pattern from Story 2.1:
```typescript
const clean = text.replace(/^```(?:json)?\n?/m, '').replace(/\n?```$/m, '').trim()
const parsed = JSON.parse(clean) as { dishes: unknown[] }
```

### DishDetailSheet Adaptation

`DishDetailSheet` has these props today:
```typescript
interface DishDetailSheetProps {
  dish: DishResult | null
  open: boolean
  onClose: () => void
  scanId: string          // ← scan-specific; search flow doesn't have a scanId
  dishIndex: number       // ← scan-specific; used for "See Full Details" URL
  onSave?: (dish: DishResult) => void
  savedId?: string
  onRemove?: (dish: DishResult) => void
}
```

The `scanId` and `dishIndex` props are used only to build `detailUrl`:
```typescript
const detailUrl = `/scan/dish?scanId=${scanId}&dishIndex=${dishIndex}`
```

For search-originated dishes there is no scan URL. Two safe approaches:

**Approach A (minimal change — preferred):** Make `scanId` and `dishIndex` optional:
```typescript
interface DishDetailSheetProps {
  // ...
  scanId?: string
  dishIndex?: number
  // ...
}
```
When `scanId` is absent or empty, the "See Full Details" link is hidden (or renders as disabled). This is a backward-compatible change — existing callers still pass both props and nothing breaks.

**Approach B:** Pass synthetic/empty values from the search page: `scanId=""` and `dishIndex={0}`. This avoids touching the component interface but the link would be broken/invalid. Not recommended.

Use Approach A. The conditional in the component becomes:
```typescript
{scanId && (
  <Link href={detailUrl} ...>See Full Details</Link>
)}
```

Existing callers (`ScanResults`) always pass `scanId` so they are unaffected.

### Evidence Block for Search-Generated Dishes

The `EvidenceBlock` component currently renders:
```
"Identified from your scan · 450 cal"
```

For search-generated dishes, the source is different. When rendering inside the search flow, consider passing a `source` hint. However, for MVP simplicity, no changes to evidence block copy are required — the existing text is acceptable. The `nutritionAvailable: false` case adds a label (see Task 4).

When `nutritionAvailable === false`, the evidence block should show "Nutrition unavailable" in place of the calorie number:
```typescript
// In EvidenceBlock, the calorie line:
{dish.calorieEstimate ? ` · ${dish.calorieEstimate} cal` : ''}
// Becomes (when nutritionAvailable is false):
{nutritionAvailable === false
  ? ' · Nutrition unavailable'
  : dish.calorieEstimate ? ` · ${dish.calorieEstimate} cal` : ''}
```

Styling: same `text-xs text-secondary` as the surrounding evidence text — no warning colours.

### Learnings from Previous Stories

**From Story 2.3 (DishDetailSheet origin):**
- `BottomSheet` uses `var(--spacing-5)` side padding internally — the full-bleed image hack uses `margin: '0 calc(var(--spacing-5) * -1)'` to break out of it. Do not change this; it is intentional.
- The `EvidenceBlock` confidence logic: `isHigh = total === 0 || highCount / total >= 0.8`. Since search-generated dishes have `ingredients: []` (at the list level), `total === 0` → `isHigh = true` → evidence block falls through to the positive confidence display. This is correct behaviour.

**From Story 3.1 (recipe save flow):**
- `useSaveRecipe` mutation returns `ApiSuccess<RecipeSaveResponse>` — access the id with `saved.data.id`
- Track saved state locally with `useState<Record<string, string>>({})` keyed by dish name (not dish index — dish names are stable)

**From Story 4.4 (offline guard):**
- `src/app/search/page.tsx` has `useOnlineStatus()` guard. The new page at `/search/restaurants/[googlePlacesId]/page.tsx` should also add this guard — if offline, show "Search requires an internet connection" message before attempting any fetch.

**From Story 2.1 (Gemini patterns):**
- Strip markdown fences before `JSON.parse`: `text.replace(/^```(?:json)?\n?/m, '').replace(/\n?```$/m, '').trim()`
- Always return `NextResponse.json(...)` — never `Response.json(...)`

**From Story 5.1 (search route patterns):**
- Both existing search routes (`/api/search/restaurants` and `/api/search/dishes`) are `GET` handlers
- The route skeleton: `import 'server-only'` → `getApiKeys()` → `try/catch` → `NextResponse.json`
