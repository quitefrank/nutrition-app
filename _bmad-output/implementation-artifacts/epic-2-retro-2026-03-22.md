## What Went Well

### Failure behavior and error states
The `emptyReason` differentiation — `image_quality`, `not_menu`, `no_dishes_found` — was identified via a party mode session before Story 2.6 implementation. The original spec had a single generic empty state. The multi-agent session (UX, PM, Architect, QA, Dev) caught that Gemini was already producing the signal and that differentiated copy would direct users toward a concrete fix rather than just acknowledging failure. The implementation is a simple lookup table — easy to extend if new signals are added.

### Party mode at the right moment
Party mode proved most valuable in the window between spec and implementation — after requirements are set but before code is written. The 2.6 party session found a real product gap, produced documentation (the Amendment in the story file), and captured the reasoning. Future sessions know *why* the copy map exists, not just *that* it does.

### Enrichment pipeline architecture
`Promise.allSettled` for parallel Google Places + USDA calls with graceful partial failure was the right choice. The pipeline degrades cleanly: Places failure → imageUrl null, USDA failure → original confidence levels, both fail → 200 with unenriched data (503 only when both API keys are missing). The fire-and-forget pattern (`void fireEnrichment()`) keeps the scan response fast.

### Test infrastructure established and reused
The framer-motion, focus-trap-react, next/navigation, and server-only mock patterns were established in Story 2.1–2.2 and reused consistently across all subsequent stories. No test-setup rework after 2.2.

### Retry flow
`lastScanParams` in scan state means retry is `submitScan` with cached args — no modal re-open, no re-capture. Users hitting a transient Gemini 503 get a one-tap recovery.

## Challenges & Learnings

### 1. Story 2.4: Index-based merge was a correctness bug
The initial enrichment implementation matched dishes by array index. Code review (P2) replaced it with name-keyed Maps. Gemini is not guaranteed to return dishes in the same order as the original scan — index-based matching would silently apply enrichment data to the wrong dishes. This is a class of bug that reads as working in happy-path tests.

**Lesson:** When merging data from two async sources, always key by a stable identifier (name, id) — never by position. Flag this explicitly in any Epic 3 story that involves save/update flows.

### 2. Story 2.4: 11 code review patches signals spec gaps
11 patches in a single code review (P1–P11) indicates the story spec didn't fully cover edge cases — input validation, timeout behaviour, API key guards, no-floating-promises, React key collisions. Some of these are mechanical (linting rules would catch P5, P6, P9), but P2 and P7 (skipHttpRedirect approach) were genuine design decisions that should have been in the spec.

**Lesson:** For stories with external API calls, spec the error path and the merge strategy explicitly. Don't leave them to implementation discovery.

### 3. Tasks 8–10 ambiguity
Tasks 8–10 were added to Story 2.3 as part of the Story 2.6 Amendment — after Story 2.3 was already marked done in sprint-status. The checkbox state in the story file diverged from the actual code: Tasks 8 and 9 were fully implemented, Task 10 (first-time tip banner) was genuinely missing. Neither the story file nor the amendment reflected reality.

**Lesson:** When an amendment adds tasks to a completed story, verify against the code immediately — don't assume "unchecked = not implemented."

### 4. Status tracking drift (same issue as Epic 1)
Epic 1 retro action item 2 was to cross-check story status before closing. It was not applied. See Previous Retro Follow-Through section above.

## Key Takeaways

1. **Process rules need hooks, not documents.** Retro action items stored only in a markdown file will not be applied. They need to fire at the point of use — story creation, story implementation — or they're invisible.
2. **Party mode earns its keep before implementation.** The 2.6 session caught a real product gap at the right moment. The mechanism works — use it proactively when a story touches UX decisions or spec ambiguity.
3. **Name-keyed merge over index-based merge.** Any time two async data sources are merged, key by stable identifier. Carry this into Epic 3.
4. **Spec the error path and merge strategy.** For external API stories, leaving edge cases to implementation discovery leads to 11-patch code reviews. Specify validation, timeouts, and merge keys upfront.
5. **Amendments must close the loop.** Adding tasks to a completed story is valid — but the status must be verified against code, not assumed.
