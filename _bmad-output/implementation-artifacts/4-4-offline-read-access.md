# Story 4.4: Offline Read Access

**Status:** ready-for-dev
**Story ID:** 4.4
**Epic:** 4 — Grocery List

---

## Story

As a user shopping in-store without reliable internet,
I want my recipe collection and grocery list to be readable offline,
So that I can reference my list and recipes even underground or in areas with poor signal.

---

## Acceptance Criteria

**AC1 — Home screen loads offline**
Given the user has opened the app at least once with an internet connection
When they lose network connectivity
Then the home screen recipe collection renders from service worker cache; loading is ≤1s (NFR03)

**AC2 — Grocery list accessible offline**
Given the user is offline
When they open the Groceries tab
Then the grocery list is fully accessible and readable; all previously loaded items are visible

**AC3 — Grocery check-off works offline**
Given the user is offline
When they tap a check circle on a grocery item
Then the item is checked off via TanStack Query optimistic update immediately; the `PUT /api/grocery/[id]` call is queued and syncs to Supabase on reconnect (background sync)

**AC4 — Scan and Search show offline message**
Given the user is offline
When they navigate to the Scan or Search screens
Then a friendly "requires an internet connection" message is shown; no crash or generic error

**AC5 — Cache-first strategy for app shell**
Given the PWA service worker is registered
When the app shell (HTML, CSS, JS bundles) is loaded
Then static assets use cache-first strategy; dynamic API responses (recipes, grocery) use network-first with cache fallback

**AC6 — Background sync on reconnect**
Given queued check-off mutations exist
When the user reconnects
Then background sync fires the pending `PUT /api/grocery/[id]` requests; TanStack Query reflects the synced state

## Dev Notes

### Architecture Compliance

| Concern | Decision | Rationale |
|---|---|---|
| PWA library | `@ducanh2912/next-pwa` | Actively maintained fork with Next.js 15 App Router support; `shadowwalker/next-pwa` has not had a release compatible with Next.js 15 RSC architecture |
| Service worker generation | Auto-generated by next-pwa / Workbox | Do NOT hand-edit `public/sw.js`; it is regenerated on every build |
| Offline detection | `useOnlineStatus()` hook | Wraps `navigator.onLine` + DOM events; must be a `'use client'` component |
| Background sync | Workbox Background Sync plugin | Progressive Enhancement — falls back gracefully if browser does not support the Background Sync API |
| Caching strategy — static | `CacheFirst` | App shell (JS/CSS/fonts) changes only on deploy; stale-while-revalidate is not needed |
| Caching strategy — API | `NetworkFirst` with cache fallback | Ensures fresh data when online; falls back to last-known-good response when offline |
| Write operations | Not cached; Background Sync for check-offs | POST/DELETE offline errors should show a toast via the existing sonner integration |

### Workbox Configuration (`next.config.ts`)

```typescript
import withPWA from '@ducanh2912/next-pwa'
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  // ...existing config
}

export default withPWA({
  dest: 'public',
  cacheOnFrontEndNav: true,
  aggressiveFrontEndNavCaching: false,
  reloadOnOnline: true,
  workboxOptions: {
    runtimeCaching: [
      {
        // API routes: recipes and grocery — NetworkFirst with offline fallback
        urlPattern: /^\/api\/(recipes|grocery)(\/.*)?$/,
        handler: 'NetworkFirst',
        options: {
          cacheName: 'plately-api-cache',
          networkTimeoutSeconds: 10,
          expiration: {
            maxEntries: 100,
            maxAgeSeconds: 24 * 60 * 60, // 24 hours
          },
          cacheableResponse: {
            statuses: [0, 200],
          },
        },
      },
    ],
  },
})(nextConfig)
```

**Excluded from cache:** `POST /api/grocery`, `PUT /api/grocery/[id]` (Background Sync handles check-offs), `DELETE` operations. These are write methods and do not match the `GET`-focused `NetworkFirst` rule above — Workbox only caches GET requests in `runtimeCaching` by default.

**Static assets** (JS bundles, CSS, fonts, icons): handled automatically by next-pwa with `CacheFirst`. No manual rule required.

### Background Sync for Grocery Check-Offs

The `PUT /api/grocery/[id]` request must be routed through the Workbox Background Sync plugin. This requires a custom service worker entry point (`src/sw.ts` or `src/service-worker.ts`), which next-pwa can merge with the generated worker via the `customWorkerSrc` option.

```typescript
// src/sw.ts  (custom additions merged into the generated service worker)
import { BackgroundSyncPlugin } from 'workbox-background-sync'
import { registerRoute } from 'workbox-routing'
import { NetworkOnly } from 'workbox-strategies'

const bgSyncPlugin = new BackgroundSyncPlugin('grocery-sync-queue', {
  maxRetentionTime: 24 * 60, // 24 hours in minutes
})

registerRoute(
  ({ url, request }) =>
    url.pathname.startsWith('/api/grocery/') && request.method === 'PUT',
  new NetworkOnly({ plugins: [bgSyncPlugin] }),
  'PUT'
)
```

Add to `next.config.ts` within the `withPWA` call:

```typescript
customWorkerSrc: 'src/sw.ts',
```

**Flow on reconnect:**
1. Browser fires the `sync` event with tag `workbox-background-sync:grocery-sync-queue`
2. Workbox replays the queued PUT requests against Supabase
3. After sync, invalidate the TanStack Query cache so the UI reflects server truth:

```typescript
// In a component or hook that listens for the sync event (optional enhancement)
// The optimistic update from story 4.2 already reflects the correct UI state.
// Cache invalidation on reconnect can be triggered by:
useEffect(() => {
  const handleOnline = () => {
    queryClient.invalidateQueries({ queryKey: ['grocery-items'] })
  }
  window.addEventListener('online', handleOnline)
  return () => window.removeEventListener('online', handleOnline)
}, [queryClient])
```

**Progressive Enhancement caveat:** Background Sync API is not supported in all browsers (notably Safari/iOS as of early 2026). On unsupported browsers the optimistic update persists locally until the page is reloaded or the user manually refreshes. Document this to end users if needed. The app does not crash — it degrades gracefully.

### `useOnlineStatus` Hook

Create `src/hooks/use-online-status.ts`:

```typescript
'use client'
import { useEffect, useState } from 'react'

/**
 * Returns true when the browser reports an active network connection.
 *
 * LIMITATION: navigator.onLine can return true even when the device has no
 * actual internet connectivity (e.g., connected to a router with no WAN).
 * This is sufficient for showing an offline message but should not be used
 * as a hard gate for security-critical operations.
 */
export function useOnlineStatus(): boolean {
  const [isOnline, setIsOnline] = useState(true)

  useEffect(() => {
    const update = () => setIsOnline(navigator.onLine)
    window.addEventListener('online', update)
    window.addEventListener('offline', update)
    // Sync with current state immediately on mount
    update()
    return () => {
      window.removeEventListener('online', update)
      window.removeEventListener('offline', update)
    }
  }, [])

  return isOnline
}
```

### Offline UI Pattern for Scan and Search

```tsx
// Example: Scan page
'use client'
import { useOnlineStatus } from '@/hooks/use-online-status'

export default function ScanPage() {
  const isOnline = useOnlineStatus()

  if (!isOnline) {
    return (
      <div className="flex flex-col items-center justify-center min-h-[60vh] gap-4 text-center px-6">
        <p className="text-2xl">No internet connection</p>
        <p className="text-muted-foreground">
          Scanning requires an internet connection. Your grocery list and saved
          recipes are still available offline.
        </p>
      </div>
    )
  }

  // ...rest of Scan page
}
```

Apply the same pattern to the Search page if it exists. The offline message should be meaningful — direct the user to the features that do work offline.

### Service Worker Constraints

- The service worker only activates on **HTTPS or `localhost`**. It will not register on plain HTTP (e.g., `http://192.168.x.x`).
- The generated `public/sw.js` and `public/workbox-*.js` files should be added to `.gitignore` since they are build artifacts. Confirm this matches the project's existing `.gitignore` policy.
- Run `next build && next start` to test the service worker — it is NOT active in `next dev` mode.
